# Python Style Guide

Применяй эти правила к новому и изменяемому Python-коду и Python-ячейкам
notebook. Правила основаны на соглашениях проекта ML3/Hw3; настройки GPU,
SSH, OpenSpec и ведения истории в этот skill не входят.
Следуй более приоритетным инструкциям и явным требованиям текущего проекта.
Не меняй окружение, зависимости или конфигурацию всего проекта без необходимости.

## Стандарт Python

- Основной стандарт — [Google Python Style Guide](https://google.github.io/styleguide/pyguide.html).
  Применять к новому и изменяемому Python-коду, включая ячейки notebook;
  не переписывать посторонний код только ради стиля.
- Использовать отступы в 4 пробела, строки до 80 символов с исключениями
  из руководства (например, неделимые URL), переносы внутри скобок
  и сгруппированные импорты. Предпочитать импорт модулей, а не отдельных
  функций и классов; исключения — по Google Python Style Guide.
- Docstring оформлять в Google style: краткая первая строка, далее
  при необходимости `Args:`, `Returns:`/`Yields:`, `Raises:`. Не добавлять
  пустые секции, очевидные описания и исключения из-за некорректного
  учебного ввода. У каждой новой или изменяемой функции должен быть
  короткий docstring о её назначении.
- Явные правила проекта имеют приоритет при отличиях от руководства:
  форматтер — `autopep8`, стиль и линтинг — Ruff; `ruff format`, Black
  и Pyink не использовать.

## Дополнения из Google Python Style Guide

### Имена, импорты и запуск

- Использовать `snake_case` для функций, переменных и модулей,
  `CapWords` для классов, `UPPER_CASE` для констант; внутренние имена
  начинать с одного `_`, не с `__`. Файлы `.py` называть без дефисов.
  Избегать неясных сокращений и имён, избыточно включающих тип.
- Короткие математические имена допустимы, если соответствуют принятой
  записи алгоритма; указать источник или пояснить обозначения.
  В публичном API предпочитать описательные имена.
- Импорты размещать в начале модуля, по одному модулю на строку:
  `__future__`, стандартная библиотека, сторонние пакеты, код проекта;
  внутри групп сортировать по полному пути без учёта регистра.
  Использовать абсолютные пути пакетов и общепринятые псевдонимы (`np`).
  Символы из `typing`, `collections.abc`, `typing_extensions` можно
  импортировать напрямую; первые два допускают несколько имён в строке.
- Исполняемую часть скрипта помещать в `main()` и вызывать под
  `if __name__ == '__main__':`. Импорт модуля не должен запускать расчёты,
  читать данные или открывать соединения. Не переносить эту обвязку
  в обычные ячейки notebook.

### Конструкции языка и состояние

- Не использовать изменяемые аргументы по умолчанию (`[]`, `{}` и т. п.)
  и значения, которые должны вычисляться при каждом вызове.
  При необходимости брать `None` и создавать объект внутри функции.
  Избегать изменяемого глобального состояния; константы допустимы.
- Проверять `None` через `is None`/`is not None`, пустые последовательности
  через `if seq`/`if not seq`. Не подменять проверку на `None` выражением
  `x or default`: оно заменит и допустимые нулевые/пустые значения.
  Для NumPy проверять пустоту через `.size`, не через `bool(array)`.
- В comprehension/генераторном выражении оставлять один `for` и не более
  одного фильтра; сложнее — обычный цикл. Итерироваться прямо по контейнеру
  или файлу, по парам словаря — через `.items()`; не создавать лишние списки
  и не менять контейнер во время обхода.
- `lambda` и условное выражение использовать только для простых случаев;
  предпочитать comprehension/генератор выражениям `map`/`filter` с `lambda`.
  Вложенные функции оправданы замыканием, а не сокрытием имени от модуля.
- Не добавлять тривиальные геттеры/сеттеры вместо публичного атрибута.
  `@property` — только для дешёвой, простой и ожидаемой логики доступа;
  дорогие операции оставлять явными методами. Вместо `staticmethod`
  предпочитать функцию модуля, `classmethod` — прежде всего для именованных
  конструкторов. Не вводить метаклассы и динамические трюки без необходимости;
  стандартные `dataclasses`, `enum` и `abc` допустимы.

### Ресурсы, ошибки и строки

- Файлы и другие закрываемые ресурсы освобождать явно через `with`,
  при необходимости `contextlib.closing()` или `try/finally`;
  не полагаться на сборщик мусора. Учитывать досрочное завершение генератора,
  если он удерживает ресурс; закрывать ненужные figure в циклах визуализации.
- Ловить конкретные исключения и сужать блок `try` до нужной операции.
  Голый `except:` и перехват `Exception` допустимы только для повторного
  проброса или явной границы изоляции с регистрацией ошибки.
  Для ошибок предпочитать стандартные классы; свои называть с суффиксом
  `Error`. Сообщение должно описывать реальную причину, а не предположение.
- Не использовать `assert` для обязательной валидации или действий алгоритма:
  оптимизация Python может его убрать. В отдельных тестах `assert` уместен.
  Это не отменяет допущение о корректном вводе ниже.
- Для форматирования строк использовать f-строки, `%` или `.format()`,
  а не цепочки `+`; при накоплении в цикле — список и `''.join()`
  или `io.StringIO`. Сохранять единый стиль кавычек в файле.
  В logging с `%`-шаблоном передавать литерал и аргументы раздельно:
  `logger.info('Count: %s', count)`, не готовую f-строку.
- В многопоточном коде не полагаться на атомарность встроенных типов:
  обмениваться данными через `queue.Queue` или явно синхронизировать доступ.

### Документация, аннотации и оформление

- Docstring заключать в `"""`, первую строку завершать знаком пунктуации;
  перед подробностями оставлять пустую строку. Описывать контракт для
  вызывающего кода, включая изменение аргументов и другие побочные эффекты,
  а не пересказывать реализацию. Типы из аннотаций не дублировать без пользы.
- `Returns:` не нужен при возврате только `None` или исчерпывающей первой
  строке. Кортеж описывать как один результат с пояснением элементов;
  `Yields:` — как выдаваемый элемент, а не объект генератора.
  У декорированной функции описывать поведение после применения декоратора.
- Модулям и классам давать краткий docstring о назначении;
  публичные атрибуты класса при необходимости описывать в `Attributes:`.
  Сохранять более строгое локальное правило о docstring каждой новой или
  изменяемой функции; не переносить послабления Google для коротких функций.
- Аннотировать новые и изменяемые публичные API, а также неочевидные типы;
  не размечать каждую очевидную локальную переменную ради полноты.
  Учитывать версию Python проекта: в современном коде использовать
  `list[T]`, `tuple[T, ...]`, `T | None`, явно указывать параметры generic.
  На входе предпочитать `Sequence`/`Mapping`, если конкретный контейнер
  не нужен; аннотация не должна обещать больше, чем поддерживает код.
  Не добавлять отдельную инфраструктуру проверки типов без необходимости.
- Не ставить `;`, не переносить код через `\`, не выравнивать присваивания
  лишними пробелами. Между определениями верхнего уровня — две пустые
  строки, между методами — одна; для аннотированного аргумента с default
  использовать пробелы: `count: int = 0`, без аннотации — `count=0`.
- Подавлять предупреждения Ruff и проверки типов точечно, по конкретному
  коду ошибки и с объяснением неочевидной причины, не отключать всё правило
  для проекта ради одной строки. В TODO указывать контекст и конкретное
  условие или срок исправления, а не неопределённое «потом».

## Форматирование и проверки

- Если инструменты недоступны, сообщить об этом; не выдавать проверку
  за выполненную и не заменять форматтер другим молча. Использовать
  окружение проекта, не устанавливать инструменты глобально без согласования.
- После каждого завершённого изменения Python-кода выполнять форматирование
  через `autopep8` и проверку через Ruff.
- Для изменённых `.py` выполнять:

  ```bash
  autopep8 --in-place <изменённые файлы>
  ruff check <изменённые файлы>
  ```

- В `.ipynb` форматировать через autopep8 только изменённые Python-ячейки,
  не JSON notebook. IPython magic и shell-команды сохранять. Проверять
  notebook через `ruff check <notebook.ipynb>`; учитывать незаполненные
  задания, не исправлять их ради линтера.
- Не применять небезопасные автоматические исправления Ruff. После правок
  запускать соответствующую короткую проверку корректности.
- Не форматировать выданные оригиналы, сторонний код и посторонние ячейки.
  Для решения и адаптации выданных тестов использовать рабочие копии,
  если проект требует сохранить оригиналы.
- Сохранять публичные интерфейсы, имена, сигнатуры и формат результатов,
  требуемые вызывающим кодом или автопроверкой, даже при отличиях от стиля.

## Читаемость и структура

- До реализации каждого пункта показывать краткий пайплайн:
  входные данные → основные этапы → ожидаемый результат. Сохранять его
  в начале соответствующего раздела notebook или документа. Отличать
  запланированную схему от реализованной и актуализировать её при изменениях.
- Следовать Zen of Python: читаемость важна; явное лучше неявного,
  простое лучше сложного, плоское лучше вложенного. Использовать понятные
  имена, прямой ход решения и минимум абстракций.
- Читаемость важнее числа строк. Не делать код плотнее ради сокращения:
  дополнительные строки допустимы, если по ним легче понять решение.
- Отделять логические части кода друг от друга пустыми строками,
  в том числе внутри одной функции.
- Разделять содержательные этапы на небольшие функции с одной задачей.
  В основной функции должна быть видна последовательность этих этапов,
  а не смешаны все подробности их реализации.
  Не дробить очевидные действия на лишние функции и абстракции.
- В notebook давать этапам отдельные ячейки и короткие Markdown-пояснения.
  Не смешивать импорты/настройки, загрузку, преобразования, расчёты
  и визуализацию в одном большом блоке.
- Сложные вычисления раскрывать через понятно названные промежуточные
  величины. Предпочитать прямой ход вычисления вложенным выражениям
  и плотным конструкциям, которые приходится мысленно расшифровывать.
- Расчёты для иллюстраций отделять от кода рисования.
  Визуализация должна читать готовые результаты, а не скрывать в себе
  этапы основного алгоритма.
- Табличные входы учебного примера записывать по одной записи на строку,
  когда это облегчает сопоставление с объяснением или рисунком.
  Неочевидную роль записи кратко пояснять рядом.
- Важные соглашения о входе и результате пояснять в docstring.
  Краткими комментариями объяснять причины неочевидных решений,
  а не пересказывать очевидный код.

## Минимальность учебного решения

- В notebook оставлять код, необходимый для решения и понимания задания:
  входы, основной алгоритм, результат и краткую визуализацию.
  Служебный учёт запусков, SHA, конфигурации, сохранение артефактов
  и проверки реализации держать во внешних скриптах.
  Обязательные требования проекта к воспроизводимости сохраняются,
  но их обслуживание не должно загромождать учебное изложение.
- Для связанных функций использовать один сквозной пример.
  Отдельные наборы данных и повторные демонстрации добавлять только
  тогда, когда они показывают необходимое отличие.
- Визуализация должна отображать входы и результаты решения.
  Не реализовывать заново сортировку, сопоставление, агрегацию
  и другие этапы алгоритма только ради таблицы или рисунка.
- Просьба добавить пояснение или иллюстрацию не означает разрешение
  добавлять универсальную инфраструктуру. Предпочитать простой рисунок,
  подпись или короткий вывод готовых значений.
- Перед изменением назвать минимальный состав решения:
  какие ячейки и функции нужны и зачем.
  Не добавлять остальные элементы «для полноты».
- Перед завершением проверить необходимость каждой добавленной части
  для условия, объяснения или обязательной проверки.
  Ненужное удалить, служебное вынести из notebook.
  Не заменять удаление лишнего кода новыми абстракциями.
- Если вспомогательный код становится длиннее основного решения,
  остановиться и пересмотреть подход. Это сигнал для упрощения,
  а не требование ужимать читаемый алгоритм.

## Корректный ввод и тесты

- Считать входные данные корректными и не добавлять проверки их корректности:
  типов, форм, размеров, координат и других значений, защитные `assert`/`raise`,
  запасные значения и `try/except`, которые лишь повторяют эту проверку.
  Явно запрошенную пользователем валидацию выполнять; более приоритетные
  требования безопасности остаются в силе.
- Ошибки стандартных операций не оборачивать без необходимости.
- Не путать валидацию ввода с самим алгоритмом: необходимые преобразования
  данных, численно устойчивые вычисления и сводки результатов сохранять.
- Проверки реализации выполнять отдельно от основного решения;
  тестами не загромождать учебные ячейки.
- Сохранять проверки безопасности на внешних границах и защиту от потери
  данных: безопасную распаковку архивов, предотвращение случайной перезаписи,
  защиту секретов и ограничения ресурсов. Допущение о корректном вводе
  не отменяет этих мер.
