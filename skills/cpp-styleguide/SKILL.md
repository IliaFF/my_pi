# C++ по стайлгайду ШАД

**Старшинство.** Условие задания и явные инструкции проекта идут первыми, конфиги проекта вторыми,
этот файл третьим. Ни одно правило здесь не отменяет требование проекта.

**Тест.** Прочитай свой diff и найди в нём лишнее — то, о чём не просили и что не нужно алгоритму.
Каждое правило ниже называет случай, где лишнее появляется.

## Перед первой правкой

1. Прочитать инструкции проекта и условие задания. В учебной задаче — `.task.yml`: разрешённые файлы,
   запрещённые конструкции, требуемые проверки. Готово, когда известно, какие файлы можно менять и что
   запускает проверяющая система.
2. Прочитать `.clang-format`, а `.clang-tidy` и `CPPLINT.cfg` — если они есть. Готово, когда настройки
   взяты из файлов, а не из памяти. Отсутствующий конфиг не создаётся без необходимости.
3. Полностью прочитать стайлгайд ШАД:
   https://raw.githubusercontent.com/yandexdataschool/algorithms/master/src/styleguide.md
   Готово, когда документ прочитан целиком в этой задаче. Перечитывать не нужно, пока он не изменился,
   не выпал из контекста и не был усечён. Если ответ пришёл частями, продолжение берётся с `nextOffset`,
   который предложил инструмент, а не с пересчёта по длине показанного текста. Недоступный документ —
   повод сказать об этом прямо, а не считать, что он прочитан.

## Простота

Входные данные корректны. Код делает работу и ничего не охраняет.

- Проверки типов, размеров, координат и других значений не пишутся. Явно заказанная валидация
  выполняется, требования безопасности и защиты от потери данных остаются в силе, и валидация ввода
  не путается с необходимыми действиями алгоритма.
- Защитных `assert`/`throw`, запасных значений и `try/catch`, повторяющих такую проверку, нет.
- Исключение и сообщение об ошибке появляются только по условию, по заказанной валидации или по
  требованию безопасности. Нужен только тип исключения — конструктор с текстом получает `""`.
- Исключения автоматических операций доходят до вызывающего.
- Асимптотика по условию соблюдается, микрооптимизации сверх неё не пишутся.
- Предпочтение отдаётся прямой реализации: без неочевидных трюков и абстракций, которые не нужны
  задаче.

## Форматирование и проверки

Форматируется только то, что изменено:

```bash
clang-format --style=file -i <файлы>
clang-format --style=file --dry-run --Werror <файлы>
```

- Посторонние файлы форматтер не трогает, логика ради форматирования не меняется.
- Логические части кода разделяются пустой строкой, в том числе внутри одной функции.
- Компиляция, доступные тесты и обязательные проверки задания выполняются в рамках изменённого кода.
  Проверку выполнить нельзя — назвать её и причину.
- Итоговый diff просматривается целиком, включая собственные новые файлы; в Git — `git diff --check`.
  Готово, когда ни один файл вне решения в diff не попал и чужие изменения не затронуты.

## Сдача учебного решения

- Ограничения `.task.yml` первичны: иногда решением служит входной файл, а не C++-код.
- По просьбе закоммитить в коммит идут только файлы решения, перечисленные поимённо. Черновики,
  тесты, условие и настройки проверяющей системы остаются вне коммита; `git add .` и
  `git commit -a` не используются.
- Push делается по просьбе пользователя и по инструкции проекта. Адреса серверов и SSH-настройки
  другого проекта не переносятся.
- Локальная проверка, успешный push и вердикт серверной проверки — три разных факта. В отчёте
  называется тот, который действительно получен.
