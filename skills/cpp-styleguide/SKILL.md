# C++ стайлгайд

## Перед изменениями

- Прочитать инструкции текущего проекта и условие задания. Для учебных задач проверить `.task.yml`: разрешённые файлы, запрещённые конструкции и требуемые проверки.
- Перед первым изменением C++-кода в текущей задаче полностью прочитать стайлгайд ШАД: https://raw.githubusercontent.com/yandexdataschool/algorithms/master/src/styleguide.md . Уже полностью прочитанный и доступный документ не перечитывать перед каждой правкой. Если ответ разбит на части, продолжать с указанного инструментом `nextOffset` (или смещения продолжения), учитывая уже прочитанный текст из fetch; не вычислять смещение по размеру отображённого ответа. Повторное чтение нужно при изменении документа, недоступности предыдущего текста или его усечении. Если документ недоступен, явно сообщить об этом; не утверждать полное соответствие без проверки.
- Полностью прочитать `.clang-format`, а также `.clang-tidy` и `CPPLINT.cfg` текущего проекта, если они существуют. Не полагаться на настройки по умолчанию или память. Если конфиг отсутствует, не создавать его без необходимости.
- При конфликте следовать явным требованиям текущего проекта и условия задания; не менять их ради этого скилла.

## Простота решений

- Предпочитать прямую, понятную реализацию без неочевидных трюков и лишних абстракций.
- Отделять логические части кода друг от друга пустыми строками,
  в том числе внутри одной функции.
- Считать входные данные корректными и не добавлять проверки их корректности: типов, размеров, координат и других значений, защитные `assert`/`throw`, запасные значения и `try/catch`, которые лишь повторяют эту проверку. Явно запрошенную пользователем валидацию выполнять; более приоритетные требования безопасности остаются в силе. Сохранять проверки безопасности и защиту от потери данных; не путать валидацию ввода с необходимыми действиями алгоритма.
- Не добавлять явные исключения и сообщения об ошибках, если они не требуются условием, явно запрошенной валидацией или требованиями безопасности и защиты данных. Если требуется только тип исключения, не придумывать текст: использовать пустую строку, когда конструктор требует сообщение.
- Не перехватывать и не подавлять автоматические исключения стандартных операций без необходимости.
- Соблюдать требуемую асимптотику, но не усложнять код микрооптимизациями.

## Форматирование и проверка

- Форматировать только изменённые C++-файлы по конфигу проекта:

```bash
clang-format --style=file -i <файлы>
clang-format --style=file --dry-run --Werror <файлы>
```

- Не форматировать посторонние файлы и не менять логику ради форматирования.
- Выполнять доступные проверки компиляции, тесты и обязательные проверки задания в рамках изменённого кода. Если проверку выполнить нельзя, явно сообщить об этом.
- Просмотреть итоговый diff, включая собственные новые файлы; не затрагивать чужие изменения. Выполнить `git diff --check`, если проект использует Git.

## Сдача учебных решений

- Соблюдать ограничения `.task.yml`: иногда решением служит входной файл, а не C++-код.
- При запросе на коммит выбирать только согласованные файлы решения; не включать посторонние черновики, тесты, условия и настройки проверяющей системы. Не использовать `git add .` и `git commit -a`.
- Делать push только по просьбе пользователя, по инструкции текущего проекта. Не переносить адреса серверов и настройки SSH из другого проекта.
- Различать локальные проверки, успешный push и результат серверной проверки; не выдавать одно за другое.
